# SOLID Principles

SOLID là 5 nguyên tắc thiết kế hướng đối tượng do **Robert C. Martin (Uncle Bob)** tổng hợp vào đầu những năm 2000. Tên viết tắt "SOLID" do Michael Feathers đặt.

Mục tiêu chung của cả 5 nguyên tắc là **quản lý sự thay đổi**. Phần mềm thực tế luôn bị yêu cầu sửa: thêm tính năng, đổi quy định, đổi công nghệ. Code được thiết kế tốt là code mà khi yêu cầu thay đổi, ta chỉ phải sửa ít chỗ, ít gây lỗi lan sang chỗ khác và ít phải kiểm tra lại.

| Ký hiệu | Nguyên tắc | Ý chính |
| ------- | ---------- | ------- |
| **S** | Single Responsibility Principle (SRP) | Một module chỉ nên có **một lý do để thay đổi**. |
| **O** | Open/Closed Principle (OCP) | Mở để mở rộng, đóng với việc sửa đổi. |
| **L** | Liskov Substitution Principle (LSP) | Class con phải thay thế được class cha mà không phá vỡ **contract** của class cha. |
| **I** | Interface Segregation Principle (ISP) | Không ép client phụ thuộc vào những **method** mà nó không sử dụng. |
| **D** | Dependency Inversion Principle (DIP) | Module cấp cao và module cấp thấp đều phụ thuộc vào abstraction; abstraction không phụ thuộc vào chi tiết. |

## 0. Thuật ngữ cần biết trước khi đọc

Tài liệu giữ nguyên thuật ngữ tiếng Anh vì đây là từ bạn sẽ gặp trong code, tài liệu và khi đi làm. Đọc lướt bảng này trước, khi gặp lại trong bài thì quay lên tra.

### Nền tảng OOP

| Thuật ngữ | Giải thích |
| --------- | ---------- |
| **Class** | Bản thiết kế mô tả dữ liệu (field) và hành vi (method) của một loại đối tượng. Ví dụ `class Order`. |
| **Object** | Một thực thể cụ thể được tạo ra từ class. `new Order()` tạo ra một object. |
| **Method** | Hàm nằm trong class, mô tả một hành vi. Ví dụ `calculateTotal()`. |
| **Interface** | Danh sách các method mà một class **cam kết sẽ có**, nhưng không chứa code xử lý cụ thể. Giống một bản hợp đồng: "ai ký thì phải làm được những việc này". |
| **Implement** | Hành động một class viết code cụ thể cho các method của interface. `class MomoPayment implements PaymentMethod`. |
| **Implementation** | Bản thân class/code cụ thể đã implement interface. `MomoPayment` là một implementation của `PaymentMethod`. |
| **Abstraction** | Cái mô tả "làm được gì" mà không nói "làm như thế nào" (thường là interface hoặc abstract class). Ngược lại với **chi tiết** (detail), là code cụ thể. |
| **Inheritance (kế thừa)** | Class con nhận lại field và method của class cha bằng `extends`. |
| **Superclass / Base type** | Class cha (hoặc interface) ở phía trên trong quan hệ kế thừa. |
| **Subclass / Subtype** | Class con kế thừa hoặc implement từ class cha / interface. |
| **Override** | Class con viết lại method đã có ở class cha để thay đổi hành vi. |
| **Polymorphism (đa hình)** | Cùng một lời gọi method nhưng mỗi object thực hiện theo cách riêng. `payment.pay()` có thể chạy code của Momo hoặc PayPal tùy object thực tế. |
| **Composition** | Thay vì kế thừa, một class **chứa** object của class khác bên trong và dùng nó. Ví dụ `UserService` chứa một `UserRepository`. |

### Thuật ngữ thiết kế

| Thuật ngữ | Giải thích |
| --------- | ---------- |
| **Module** | Một đơn vị code có ranh giới rõ ràng. Trong bài này có thể hiểu đơn giản là **một class** (ở quy mô lớn hơn có thể là một file, package hay service). |
| **Dependency (phụ thuộc)** | A phụ thuộc vào B nghĩa là A **dùng** B (gọi method, tạo object, nhắc tên B trong code). Khi B thay đổi, A có thể bị ảnh hưởng. |
| **Client** | Code **sử dụng** một class hay interface khác. Nếu `PaymentService` gọi `payment.pay()`, thì `PaymentService` là client của `PaymentMethod`. Không phải "client" trong client–server. |
| **Contract** | Những cam kết về hành vi của một class/method: nhận đầu vào gì, trả kết quả gì, có ném lỗi không, luôn đảm bảo điều gì. Một phần contract nằm trong code (tên method, kiểu dữ liệu), phần còn lại nằm trong tài liệu và kỳ vọng của người dùng. |
| **Business logic (logic nghiệp vụ)** | Code thể hiện quy tắc của bài toán thực tế: cách tính tiền, điều kiện được giảm giá, quy trình duyệt đơn... Phân biệt với code kỹ thuật như lưu database, gửi email. |
| **Requirement** | Yêu cầu về chức năng hoặc hành vi mà phần mềm phải đáp ứng. |
| **Stakeholder** | Người hoặc nhóm có quyền lợi liên quan đến phần mềm và có thể đưa ra yêu cầu: khách hàng, kế toán, quản lý, đội vận hành... |
| **Actor** | Một nhóm stakeholder có cùng nhu cầu, **có thể yêu cầu thay đổi một phần code**. Xem giải thích chi tiết ở phần SRP. |

### Thuật ngữ quy trình & kỹ thuật

| Thuật ngữ | Giải thích |
| --------- | ---------- |
| **Regression** | Lỗi xuất hiện ở chức năng **trước đây đang chạy đúng**, do vừa sửa code ở chỗ khác. |
| **Merge conflict** | Khi hai người cùng sửa một đoạn code trong Git, Git không tự gộp được và bắt phải xử lý tay. |
| **Refactor** | Sắp xếp lại cấu trúc code cho tốt hơn mà **không thay đổi hành vi** bên ngoài. |
| **Compile time / Runtime** | Compile time là lúc biên dịch code, lỗi bị phát hiện trước khi chạy. Runtime là lúc chương trình đang chạy, lỗi lúc này có thể làm sập chương trình. Phát hiện lỗi ở compile time luôn tốt hơn. |
| **Exception** | Lỗi được "ném" ra khi chạy chương trình. `UnsupportedOperationException` là exception báo "thao tác này không được hỗ trợ". |
| **`instanceof`** | Toán tử Java kiểm tra một object có thuộc class nào không. Ví dụ `if (bird instanceof Penguin)`. |
| **Unit test** | Đoạn code tự động kiểm tra một đơn vị nhỏ (thường là một class/method) có chạy đúng không. |
| **Mock** | Object giả lập dùng trong test để thay thế dependency thật (ví dụ giả lập database để test không cần database thật). |
| **Factory** | Một class/method chuyên nhiệm vụ **tạo object**, quyết định tạo loại nào dựa trên điều kiện. |
| **Dependency Injection (DI)** | Kỹ thuật đưa dependency **từ bên ngoài vào** (thường qua constructor) thay vì class tự `new` bên trong. |
| **DI container** | Công cụ của framework (Spring, NestJS, Laravel...) tự động tạo object và inject dependency giúp ta. |
| **KISS** | *Keep It Simple, Stupid* — giữ code đơn giản nhất có thể. |
| **YAGNI** | *You Aren't Gonna Need It* — đừng viết trước những thứ chưa chắc sẽ cần. |

## 1. S — Single Responsibility Principle

> **A module should have one, and only one, reason to change.**
>
> *Một module chỉ nên có một, và chỉ một, lý do để thay đổi.*

### "Lý do để thay đổi" là gì? Hiểu qua khái niệm Actor

Code không tự nhiên thay đổi. Code thay đổi vì **có người yêu cầu** thay đổi nó. Vì vậy, Uncle Bob diễn đạt lại SRP rõ hơn:

> **A module should be responsible to one, and only one, actor.**
>
> *Một module chỉ nên chịu trách nhiệm trước một actor duy nhất.*

**Actor** là một người hoặc một nhóm người **có cùng nhu cầu** và **có quyền yêu cầu thay đổi** một phần hành vi của phần mềm. Actor thường tương ứng với một phòng ban hoặc một vai trò trong tổ chức, ví dụ: phòng kế toán, phòng nhân sự, đội vận hành hệ thống, bộ phận chăm sóc khách hàng.

Lưu ý: "actor" ở đây **không phải** là một người cụ thể, cũng không phải một object trong code. Nó là **nguồn gốc của các yêu cầu thay đổi**.

Cách tìm actor của một class: với mỗi method, hãy hỏi **"Ai sẽ là người yêu cầu sửa method này?"**. Nếu câu trả lời là nhiều nhóm khác nhau, class đó đang phục vụ nhiều actor và vi phạm SRP.

**Ví dụ đời thường:** một nhân viên cùng lúc báo cáo cho trưởng phòng kế toán, trưởng phòng nhân sự và trưởng phòng IT. Ba người có thể giao việc mâu thuẫn nhau, và khi làm theo yêu cầu của người này, nhân viên dễ làm hỏng việc của người kia. Một class phục vụ nhiều actor gặp đúng vấn đề này.

### Ví dụ kinh điển: chuyện gì xảy ra khi một class phục vụ nhiều actor

Ví dụ dưới đây dựa trên ví dụ Uncle Bob dùng trong sách *Clean Architecture*:

```java
class Employee {

    // Phòng kế toán dùng để tính lương
    double calculatePay() {
        return regularHours() * hourlyRate;
    }

    // Phòng nhân sự dùng để báo cáo giờ làm
    String reportHours() {
        return "Giờ làm chuẩn: " + regularHours();
    }

    // Đội kỹ thuật/DBA quan tâm cách lưu dữ liệu
    void save() { ... }

    // Hàm phụ dùng chung cho cả 2 method trên
    private double regularHours() { ... }
}
```

Ba method thuộc về **ba actor khác nhau**:

| Method | Actor yêu cầu thay đổi |
| ------ | ---------------------- |
| `calculatePay()` | Phòng kế toán |
| `reportHours()` | Phòng nhân sự |
| `save()` | Đội kỹ thuật / DBA |

Giả sử phòng kế toán yêu cầu đổi cách tính giờ chuẩn để tính lương. Lập trình viên sửa `regularHours()`, test lại phần tính lương, thấy đúng và đưa lên production.

Nhưng `reportHours()` của phòng nhân sự **cũng dùng `regularHours()`**. Báo cáo giờ làm của nhân sự giờ đã sai, mà không ai hay biết, vì người sửa chỉ nghĩ đến yêu cầu của kế toán. Đây chính là **regression** do một class phục vụ nhiều actor.

Ngoài ra, nếu một lập trình viên sửa tính lương và một người khác sửa cách lưu database cùng lúc, cả hai cùng sửa file `Employee.java`, dẫn tới **merge conflict**.

### Hiểu lầm phổ biến

SRP **không** có nghĩa là "một class chỉ làm một việc" hay "một class chỉ có một method". Một class có thể có nhiều method, miễn là tất cả **cùng phục vụ một actor** và cùng thay đổi vì một lý do.

### Áp dụng vào ví dụ `Order`

```java
class Order {
    double calculateTotal() { ... }   // Actor: bộ phận kinh doanh (quy tắc tính tiền, giảm giá)
    void saveToDatabase() { ... }     // Actor: đội kỹ thuật (schema, loại database)
    void sendEmail() { ... }          // Actor: chăm sóc khách hàng (nội dung thông báo)
    void exportPdf() { ... }          // Actor: kế toán (mẫu hóa đơn)
}
```

`Order` đang phục vụ **4 actor**, tức có **4 lý do để thay đổi**.

Cách tách:

```java
class Order {
    double calculateTotal() { ... }
}

class OrderRepository {
    void save(Order order) { ... }
}

class OrderEmailNotifier {
    void sendConfirmation(Order order) { ... }
}

class OrderPdfExporter {
    byte[] export(Order order) { ... }
}
```

**Tại sao tốt hơn?**

* Khi đổi cách lưu database, chỉ sửa `OrderRepository`.
* Khi đổi nội dung email, chỉ sửa `OrderEmailNotifier`.
* Mỗi actor có "khu vực" code riêng, sửa cho actor này không ảnh hưởng actor khác.
* `Order` chỉ còn business logic, nên dễ viết unit test mà không cần database hay mail server.

**Lưu ý:** Chỉ tách khi các actor khác nhau là **có thật** hoặc rất rõ ràng. Tách theo phỏng đoán sẽ sinh ra quá nhiều class nhỏ, khó theo dõi luồng code.

## 2. O — Open/Closed Principle

> **Software entities should be open for extension, but closed for modification.**
>
> *Các thành phần phần mềm nên mở cho việc mở rộng, nhưng đóng với việc sửa đổi.*

Nguyên tắc này được Bertrand Meyer đưa ra năm 1988. Uncle Bob diễn giải lại theo hướng dùng abstraction và polymorphism:

* **Open for extension (mở để mở rộng):** có thể thêm hành vi mới.
* **Closed for modification (đóng với sửa đổi):** việc thêm đó **không cần sửa code cũ** đã chạy ổn định, mà bằng cách **viết code mới**.

### Ví dụ vi phạm

```java
class PaymentService {

    void pay(String type, double amount) {
        if (type.equals("CREDIT_CARD")) {
            // ...
        } else if (type.equals("PAYPAL")) {
            // ...
        } else if (type.equals("MOMO")) {
            // ...
        }
    }
}
```

Mỗi khi thêm phương thức thanh toán mới, ta phải mở `PaymentService` ra sửa. Mỗi lần sửa có nguy cơ làm hỏng các nhánh đang chạy đúng (regression), và phải test lại toàn bộ.

### Thiết kế theo OCP

Tạo một **abstraction** (interface) mô tả "thanh toán được":

```java
interface PaymentMethod {
    void pay(double amount);
}
```

Mỗi phương thức thanh toán là một **implementation** riêng:

```java
class CreditCardPayment implements PaymentMethod {
    public void pay(double amount) { ... }
}

class PaypalPayment implements PaymentMethod {
    public void pay(double amount) { ... }
}

class MomoPayment implements PaymentMethod {
    public void pay(double amount) { ... }
}
```

`PaymentService` chỉ làm việc với interface, không quan tâm implementation cụ thể (đây là **polymorphism**):

```java
class PaymentService {

    void process(PaymentMethod payment, double amount) {
        payment.pay(amount);
    }
}
```

Khi cần thêm chuyển khoản ngân hàng, ta **viết thêm một class mới**:

```java
class BankTransferPayment implements PaymentMethod {
    public void pay(double amount) { ... }
}
```

`PaymentService` **không cần sửa**.

### Hai điểm cần hiểu đúng

1. **Logic chọn implementation không biến mất, nó được dời đi.** Vẫn phải có một nơi quyết định dùng `MomoPayment` hay `PaypalPayment` dựa trên lựa chọn của người dùng. Nơi đó thường là một **Factory**, một `Map<String, PaymentMethod>` hoặc **DI container**. Điểm khác biệt là nơi đó tách khỏi business logic, và việc thêm mới chỉ là đăng ký thêm một implementation.
2. **Không có code nào "đóng" với mọi loại thay đổi.** Ta phải chọn **trục mở rộng** (hướng mà code dễ được mở rộng) dựa trên những gì thực sự hay thay đổi. Ở ví dụ này, thứ hay thay đổi là phương thức thanh toán. Đặt abstraction sai chỗ còn tệ hơn không có abstraction.

## 3. L — Liskov Substitution Principle

Đây thường là nguyên tắc **khó hiểu nhất**. Nguyên tắc do nhà khoa học máy tính Barbara Liskov đưa ra năm 1987.

> Nếu `S` là subtype của `T`, thì ở bất kỳ đâu chương trình dùng `T`, ta có thể thay bằng `S` mà chương trình vẫn hoạt động đúng theo những gì `T` đã cam kết.

Nói đơn giản: **class con phải dùng được ở mọi chỗ class cha được dùng, mà không gây bất ngờ.**

### Ví dụ kinh điển

```java
class Bird {
    void fly() { ... }
}

class Sparrow extends Bird {   // Chim sẻ
    @Override
    void fly() { ... }
}

class Penguin extends Bird {   // Chim cánh cụt
    @Override
    void fly() {
        throw new UnsupportedOperationException();
    }
}
```

Code sử dụng (client):

```java
void makeBirdFly(Bird bird) {
    bird.fly();
}

makeBirdFly(new Penguin()); // Lỗi khi chạy (runtime exception)
```

Class `Bird` có method `fly()`, tức là nó **cam kết** (contract): "mọi con chim đều bay được". Client tin vào cam kết này nên gọi `fly()` mà không kiểm tra gì. `Penguin` không giữ được cam kết đó nên chương trình bị lỗi.

Vấn đề không nằm ở `Penguin` mà ở **abstraction đặt sai**:

```text
Bird (fly)
 ├── Sparrow
 └── Penguin   ← không thực hiện được contract
```

### Thiết kế lại

```java
interface Bird {
    void eat();
}

interface FlyingBird extends Bird {
    void fly();
}

class Sparrow implements FlyingBird {
    public void eat() { ... }
    public void fly() { ... }
}

class Penguin implements Bird {
    public void eat() { ... }
}
```

Bây giờ `makeBirdFly(FlyingBird bird)` chỉ nhận những loài thực sự bay được. Nếu ai đó truyền `Penguin` vào, **compiler báo lỗi ngay ở compile time** thay vì để chương trình sập lúc runtime.

### Bản chất của LSP

LSP không chỉ là "class con có đủ các method của class cha" (điều này compiler đã tự kiểm tra). LSP yêu cầu **class con phải tuân thủ contract về hành vi** của class cha. Contract gồm ba phần:

| Phần | Giải thích | Quy tắc cho class con |
| ---- | ---------- | --------------------- |
| **Precondition** (điều kiện đầu vào) | Điều kiện phải đúng **trước khi** gọi method. Ví dụ: `amount > 0`. | Không được **đòi hỏi chặt hơn** class cha. Nếu cha nhận mọi `amount > 0`, con không được chỉ nhận `amount > 100`. |
| **Postcondition** (kết quả đảm bảo) | Điều method cam kết là đúng **sau khi** chạy xong. Ví dụ: "trả về danh sách không null". | Không được **đảm bảo ít hơn** class cha. Nếu cha không bao giờ trả `null`, con cũng không được trả `null`. |
| **Invariant** (tính chất bất biến) | Điều **luôn luôn đúng** với object. Ví dụ: "số dư tài khoản không bao giờ âm". | Class con phải giữ nguyên. |

Dấu hiệu thường gặp của vi phạm LSP:

* Subclass `throw UnsupportedOperationException` cho method kế thừa.
* Subclass override method thành rỗng hoặc trả về giá trị vô nghĩa.
* Client phải kiểm tra `instanceof` để xử lý riêng từng subclass. Trường hợp này đồng thời vi phạm cả OCP, vì mỗi khi có subclass mới lại phải sửa client.

**Bài học rút ra:** quan hệ "là một" (is-a) trong đời thực (chim cánh cụt *là* chim, hình vuông *là* hình chữ nhật) không đảm bảo quan hệ kế thừa đúng trong code. Trong code, điều quan trọng là **hành vi** có tương thích không. Đây là một lý do chính để **ưu tiên composition hơn inheritance**.

## 4. I — Interface Segregation Principle

> **Clients should not be forced to depend on methods they do not use.**
>
> *Client không nên bị ép phụ thuộc vào những method mà nó không sử dụng.*

Chữ quan trọng ở đây là **client**, tức code *gọi* interface, chứ không chỉ class *implement* interface. Interface nên được thiết kế theo **nhu cầu của người dùng nó**, không theo những gì một class có thể làm.

### Ví dụ vi phạm

```java
interface Worker {
    void work();
    void eat();
}
```

```java
class Human implements Worker {
    public void work() { ... }
    public void eat() { ... }
}

class Robot implements Worker {
    public void work() { ... }

    public void eat() {
        throw new UnsupportedOperationException(); // Bị ép implement
    }
}
```

Interface `Worker` quá to (còn gọi là **fat interface**), gây ra hai vấn đề:

1. **Phía implement:** `Robot` bị ép viết method vô nghĩa, và điều này dẫn tới vi phạm LSP.
2. **Phía client:** giả sử có `TaskScheduler` (bộ phân công việc) chỉ cần gọi `work()`, nhưng lại phải nhận cả `Worker`. Khi ai đó sửa method `eat()` trong `Worker`, `TaskScheduler` cũng có thể bị ảnh hưởng (phải biên dịch lại, có khi phải sửa) dù nó chẳng liên quan gì đến việc ăn.

### Tách interface theo nhu cầu client

```java
interface Workable {
    void work();
}

interface Eatable {
    void eat();
}
```

```java
class Human implements Workable, Eatable {
    public void work() { ... }
    public void eat() { ... }
}

class Robot implements Workable {
    public void work() { ... }
}
```

Mỗi client chỉ phụ thuộc đúng phần nó cần:

```java
class TaskScheduler {
    void assign(Workable worker) { worker.work(); }
}

class CanteenService {          // Dịch vụ căng tin
    void serve(Eatable eater) { eater.eat(); }
}
```

ISP giúp interface **nhỏ, tập trung và đúng nhu cầu của client**.

## 5. D — Dependency Inversion Principle

Đây là nguyên tắc rất quan trọng khi thiết kế backend. DIP gồm hai ý:

> 1. **Module cấp cao không nên phụ thuộc vào module cấp thấp. Cả hai nên phụ thuộc vào abstraction.**
> 2. **Abstraction không nên phụ thuộc vào chi tiết. Chi tiết nên phụ thuộc vào abstraction.**

Giải thích thuật ngữ:

* **Module cấp cao (high-level):** chứa business logic, là "bộ não" của ứng dụng. Ví dụ `UserService` quyết định quy trình tạo user.
* **Module cấp thấp (low-level):** chứa chi tiết kỹ thuật để thực hiện công việc. Ví dụ code kết nối MySQL, gọi API bên ngoài, gửi email.

Lý do cần DIP: business logic là thứ quý giá và ổn định nhất của ứng dụng. Chi tiết kỹ thuật (dùng MySQL hay PostgreSQL, gửi mail qua dịch vụ nào) thì hay thay đổi. Không nên để thứ quý giá bị kéo theo mỗi khi thứ hay thay đổi bị thay.

### Ví dụ vi phạm

```java
class MySQLDatabase {
    void save(User user) { ... }
}

class UserService {

    private final MySQLDatabase database = new MySQLDatabase();

    void createUser(User user) {
        database.save(user);
    }
}
```

`UserService` tự `new MySQLDatabase()`, tức phụ thuộc trực tiếp vào chi tiết:

* Muốn chuyển sang PostgreSQL thì phải sửa `UserService`.
* Không thể viết unit test cho `UserService` mà không có MySQL thật, vì không có cách thay bằng mock.

```text
UserService ──→ MySQLDatabase
(cấp cao)        (cấp thấp)
```

### Thiết kế theo DIP

Bước 1: tạo abstraction mô tả nhu cầu của tầng nghiệp vụ.

```java
interface UserRepository {
    void save(User user);
}
```

Bước 2: các chi tiết kỹ thuật implement abstraction đó.

```java
class MySQLUserRepository implements UserRepository {
    public void save(User user) { ... }
}

class PostgreSQLUserRepository implements UserRepository {
    public void save(User user) { ... }
}
```

Bước 3: `UserService` chỉ biết đến interface, và nhận implementation **từ bên ngoài** qua constructor (đây là Dependency Injection).

```java
class UserService {

    private final UserRepository repository;

    UserService(UserRepository repository) {
        this.repository = repository;
    }

    void createUser(User user) {
        repository.save(user);
    }
}
```

```java
// Nơi lắp ráp (thường do DI container của framework làm)
UserService service = new UserService(new PostgreSQLUserRepository());

// Trong unit test, truyền vào object giả lập
UserService testService = new UserService(new FakeUserRepository());
```

Chiều phụ thuộc bây giờ:

```text
       UserService ──────→ UserRepository (interface)
                                 ↑            ↑
                                 │            │
                 MySQLUserRepository   PostgreSQLUserRepository
```

Mũi tên là chiều **phụ thuộc** (A → B nghĩa là A biết đến và dùng B). Cả `UserService` lẫn các implementation đều trỏ vào `UserRepository`.

**Vì sao gọi là "Inversion" (đảo ngược)?** Ở thiết kế cũ, module cấp thấp nằm "dưới", module cấp cao phụ thuộc xuống nó. Ở thiết kế mới, module cấp thấp phải phụ thuộc **ngược lên** abstraction do tầng cấp cao đặt ra. Chiều phụ thuộc của module cấp thấp đã bị đảo ngược.

### Chi tiết quan trọng: abstraction thuộc về ai?

Để DIP có ý nghĩa, interface `UserRepository` phải được định nghĩa **theo nhu cầu của tầng nghiệp vụ** và đặt cùng tầng với `UserService`, không đặt trong phần code của MySQL. Nếu interface chỉ là bản sao các method của `MySQLDatabase`, ta vẫn đang gián tiếp phụ thuộc vào chi tiết.

```text
domain/                         ← tầng nghiệp vụ
 ├── UserService
 └── UserRepository             ← interface do tầng nghiệp vụ sở hữu
infrastructure/                 ← tầng chi tiết kỹ thuật
 ├── MySQLUserRepository        ← implement interface của domain
 └── PostgreSQLUserRepository
```

### DIP và Dependency Injection khác nhau

Hai khái niệm này có tên gần giống nhau nên rất hay bị nhầm.

| | Dependency Inversion (DIP) | Dependency Injection (DI) |
| - | - | - |
| Bản chất | **Nguyên tắc** thiết kế về chiều phụ thuộc | **Kỹ thuật** đưa dependency từ bên ngoài vào |
| Trả lời câu hỏi | Nên phụ thuộc vào cái gì? (abstraction hay chi tiết) | Dependency được tạo và đưa vào ở đâu? |

DI là một cách phổ biến để **hiện thực** DIP. Các framework như Spring (Java), NestJS (TypeScript) hay Laravel (PHP) cung cấp DI container để tự động hóa việc này. Tuy nhiên, có DI chưa chắc đã có DIP: nếu ta inject trực tiếp class cụ thể `MySQLUserRepository` vào `UserService`, đó vẫn là DI nhưng không đạt DIP.

# Nhìn cả SOLID dưới một góc độ

Có thể dùng 5 nguyên tắc như một bộ câu hỏi khi viết hoặc review code:

| Nguyên tắc | Câu hỏi cần đặt ra |
| ---------- | ------------------ |
| **S — SRP** | Class này phục vụ bao nhiêu actor? Có bao nhiêu nhóm người có thể yêu cầu sửa nó? |
| **O — OCP** | Thêm một biến thể mới có buộc phải sửa code cũ đang chạy ổn không? |
| **L — LSP** | Class con có thực sự giữ đúng contract về hành vi của class cha không? |
| **I — ISP** | Client có đang phụ thuộc vào những method nó không dùng không? |
| **D — DIP** | Business logic có đang phụ thuộc trực tiếp vào chi tiết kỹ thuật không? |

Cách nhớ nhanh:

```text
S → Một actor, một lý do để thay đổi
O → Mở rộng bằng code mới, không sửa code cũ
L → Giữ đúng contract
I → Interface vừa đủ cho client
D → Phụ thuộc vào abstraction
```

### Các nguyên tắc liên kết với nhau

* Vi phạm **ISP** (interface quá to) thường dẫn tới vi phạm **LSP** (implement method bằng cách throw exception).
* Vi phạm **LSP** thường dẫn tới vi phạm **OCP** (client phải `instanceof` và sửa mỗi khi có subclass mới).
* **DIP** là cơ chế chính để đạt được **OCP**: nhờ phụ thuộc vào abstraction, ta thêm implementation mới mà không sửa code dùng nó.
* **SRP** xác định ranh giới của từng module, từ đó mới biết nên áp dụng 4 nguyên tắc còn lại ở đâu.

### Một điểm cực kỳ quan trọng

**SOLID không có nghĩa là tách class/interface càng nhiều càng tốt.**

Ví dụ một class chỉ có:

```java
class Calculator {
    int add(int a, int b) {
        return a + b;
    }
}
```

thì không cần biến thành:

```text
CalculatorInterface
CalculatorImpl
CalculatorFactory
CalculatorService
...
```

chỉ để "đạt SOLID".

Mỗi abstraction đều có cái giá phải trả: thêm file, thêm tầng gián tiếp, khó theo dõi luồng code hơn. SOLID đáng đầu tư nhất ở phần **business logic cốt lõi, sống lâu và thay đổi thường xuyên**. Với script dùng một lần hay bản thử nghiệm (prototype), các nguyên tắc **KISS** và **YAGNI** thường quan trọng hơn.

SOLID là **nguyên tắc thiết kế**, không phải checklist bắt buộc.

Một thước đo thực dụng: **nếu unit test cho một class rất khó viết** (phải dựng database thật, không thay được dependency bằng mock, phải chuẩn bị quá nhiều thứ), gần như chắc chắn class đó đang vi phạm SRP hoặc DIP.

Mục tiêu cuối cùng:

```text
Code dễ hiểu
     ↓
Dễ thay đổi
     ↓
Dễ test
     ↓
Ít phụ thuộc
     ↓
Ít ảnh hưởng dây chuyền
```
